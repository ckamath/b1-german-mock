## 1. Agentic Commerce Protocol (ACP, OpenAI + Stripe): how it works, version, adoption, limits

### Takeaway
ACP is a beta, Apache-2.0, date-versioned retail-checkout spec (latest stable: 2026-04-17) whose building blocks are a product feed, a merchant-hosted checkout-session API, and a delegated-payment token scoped to merchant + amount + expiry (Stripe's Shared Payment Token being the first implementation). Its flagship deployment, ChatGPT Instant Checkout, was scaled back in March 2026 (checkout moved into merchant "Apps"), and nothing found shows ACP checkout live for German consumers as of November 2026.

### Cited Findings
- Launch: Instant Checkout in ChatGPT launched 29 Sep 2025 with US Etsy sellers, single-item purchases only, Shopify merchants to follow; merchants pay a fee on completed purchases. ACP was released the same day as an open standard co-developed by Stripe and OpenAI. — [Stripe newsroom](https://stripe.com/newsroom/news/stripe-openai-instant-checkout); [TechCrunch, 29 Sep 2025](https://techcrunch.com/2025/09/29/openai-takes-on-google-amazon-with-new-agentic-shopping-system)
- Versions (date-based): 2025-09-29 (initial), 2025-12-12 (fulfillment changes), 2026-01-16 (capability negotiation), 2026-01-30 (extensions, discounts, payment handlers), 2026-04-17 (cart, feed, orders, authentication, MCP). 2026-04-17 is the latest stable version; the spec is still labelled "beta". — [Stripe ACP docs](https://docs.stripe.com/agentic-commerce/protocols/acp); [Swell explainer](https://www.swell.is/content/agentic-commerce-protocol-explained)
- 2026-04-17 content (per secondary summaries of the changelog): carts, a Feed API (`POST /feeds`, `PATCH /feeds/{id}/products`; recommended one full upload per day plus intraday price/availability updates), native orders, Delegate Authentication (3DS2), a `/.well-known/acp.json` discovery document, an MCP transport binding mapping the five checkout endpoints to tools such as `create_checkout_session` / `complete_checkout_session`, mandatory `Idempotency-Key` on all checkout and delegated-payment POSTs, a defined webhook signature format, seller-backed payment handlers. — [ACP changelog](https://agenticcommerce.dev/docs/changelog); [commercetools deep dive](https://commercetools.com/blog/agentic-commerce-protocol-acp-deep-dive-guide)
- Conflict: one source describes the Feed API as an "unreleased" surface, others as shipped in 2026-04-17. Also an open issue reports six fields in the 2026-04-17 checkout schema declared in JSON Schema but rejected by the OpenAPI document. — [safeguard.sh explainer](https://safeguard.sh/resources/blog/agentic-commerce-protocol-explained-checkout-endpoints-delegated-payments-and-agent-risks)
- Delegated payment: OpenAI's Delegated Payment Spec restricts the token by a maximum amount and expiry; Stripe's Shared Payment Token (SPT) is scoped to a specific merchant and cart total and is "the first Delegated Payment Spec-compatible implementation", with "more PSPs coming soon". — [OpenAI Delegated Payment Spec](https://developers.openai.com/commerce/specs/payment); [OpenAI key concepts](https://developers.openai.com/commerce/guides/key-concepts)
- Governance conflict: Stripe docs describe ACP as created by "Stripe, OpenAI, and Meta"; a third-party explainer says Apache 2.0, maintained by OpenAI and Stripe. — [Stripe ACP docs](https://docs.stripe.com/agentic-commerce/protocols/acp); [Swell](https://www.swell.is/content/agentic-commerce-protocol-explained)
- Pull-back: in early March 2026 The Information reported OpenAI was backing away from native checkout in ChatGPT; an OpenAI spokesperson: "Instant Checkout is moving to Apps, where purchases can happen more seamlessly." Reasons reported: users research in ChatGPT but do not complete purchases there; only a small number of merchants were actively using native checkout. ACP itself continues as the connecting infrastructure. — [Digital Commerce 360, 6 Mar 2026](https://www.digitalcommerce360.com/2026/03/06/openai-shifts-checkout-plans-agentic-commerce-strategy/); [Search Engine Land](https://searchengineland.com/chatgpt-instant-checkout-plan-change-471033)
- OpenAI's docs state Instant Checkout in ChatGPT is "currently available to approved partners"; on 24 Mar 2026 OpenAI said the initial version "did not offer the level of flexibility" it wanted. — [OpenAI key concepts](https://developers.openai.com/commerce/guides/key-concepts)
- Vendor reading (Checkout.com, 20 Apr 2026): the change is a shift in "who controls the checkout", not where it happens. — [Checkout.com blog](https://checkout.com/blog/openai-agentic-commerce-shift)
- Scope claim (vendor explainer): ACP covers physical and digital goods, subscriptions, and asynchronous purchases. — [Checkout.com Q&A](https://www.checkout.com/blog/agentic-commerce-questions-answered)
- Germany: at Stripe Tour Berlin 2026 Stripe announced that "from later in 2026" German businesses can make products discoverable and purchasable inside AI interfaces via the Agentic Commerce Suite (single integration); businesses with US entities can already sell to US customers through platforms including Gemini and Copilot. Announced, not confirmed shipped. — [Stripe newsroom, Tour Berlin 2026](https://stripe.com/newsroom/news/stripe-tour-berlin-2026); [The Paypers](https://thepaypers.com/payments/news/stripe-launches-tools-for-german-businesses-to-sell-via-ai-agents)

### Inferences
- ACP's object model (feed -> cart -> checkout session -> delegated payment -> order) is a retail SKU model. Nothing in the extracts shows objects for quotes computed from personal data, pre-contractual disclosures, contract start dates, or cancellation of a third-party contract; a comparison platform would have to carry those in custom extensions.
- SPT scoping (one merchant, one amount, one expiry) fits one-off purchases; the "subscriptions" claim comes from a vendor blog and should be verified in the spec before the report relies on it.
- OpenAI's retreat to Apps means the merchant (or an aggregator like a comparison portal) keeps the checkout and the customer relationship, which is favourable for a Check24-type intermediary exposing its own app/MCP surface.

### Gaps
- Could not read the spec, so the exact semantics of subscriptions, payment-handler list (which non-card methods), and the 2026-04-17 authentication model are unverified.
- No source found on ACP/Instant Checkout availability for consumers in Germany/EU as of Nov 2026, nor on whether Stripe's German Agentic Commerce Suite launch actually happened.
- No adoption numbers (merchants, GMV) found.

## 2. Agent Payments Protocol (AP2, Google): mandates, credentials, HP vs HNP, status, partners

### Takeaway
AP2 is the authorization/evidence layer: user-signed verifiable credentials ("mandates") prove what an agent was allowed to buy. The original Sept 2025 design had Intent, Cart and Payment Mandates; v0.2 (reported 28 Apr 2026) restructures this into Checkout and Payment Mandates in "open" (constraints, human-not-present) and "closed" (final, human-present) forms secured as SD-JWTs, and Google has contributed AP2 to the FIDO Alliance alongside Mastercard's Verifiable Intent.

### Cited Findings
- Launch 16 Sep 2025 as an open protocol with 60+ partners. Intent Mandate records the user's request and rules; Cart Mandate locks specific items and price; Payment Mandate signals to networks/issuers that an agent carried out the transaction. A detailed Intent Mandate lets the agent create the Cart Mandate later without the user present. — [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol/?hl=en); [TechCrunch, 16 Sep 2025](https://techcrunch.com/2025/09/16/google-launches-new-protocol-for-agent-driven-purchases)
- Current spec on GitHub is labelled v0.2 and defines two mandate types, Checkout Mandate and Payment Mandate, each linked to a receipt. Human Present: the user approves closed mandates directly. Human Not Present: the user approves open constraints that the agent later converts into closed mandates. — [AP2 specification (GitHub)](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md); [AP2 flows](https://ap2-protocol.org/ap2/flows/)
- Credential format: SD-JWTs secure Payment and Checkout Mandates; open mandates must carry the agent's public key in a `cnf` claim; shopping agents must not present a subsequent open mandate without a rejection receipt for the previous one. A secondary source says the closed mandate in HNP mode is a Key-Binding JWT over the open one (draft "Delegate SD-JWT"; unverified). — [AP2 specification (GitHub)](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md); [replyant analysis](https://replyant.com/lab/ap2-agent-payments-protocol/)
- AP2 spec claims standardized flows for recurring payments and subscriptions and support for human-not-present scenarios (spec's own claim). — [AP2 specification](https://ap2-protocol.org/ap2/specification/)
- FIDO: AP2 and Mastercard's Verifiable Intent were contributed to the FIDO Alliance; Verifiable Intent is a protocol-agnostic layer at v0.1. A Substack post dates Google's "we're donating AP2 to the FIDO Alliance" and the v0.2 release to 28 Apr 2026 (single secondary source for the date). — [FIDO Alliance CTO post](https://fidoalliance.org/building-the-trust-layer-for-agentic-payments-with-ap2-and-verifiable-intent/); [Substack: AP2 mandates explained](https://pritamr.substack.com/p/agent-payments-protocol)
- Layering: UCP and ACP operate at the commerce layer; AP2 proves the agent has permission to act for the shopper. — [PYMNTS vocab playbook](https://www.pymnts.com/?p=4266062)
- Partners named in coverage include Mastercard, Adyen, PayPal; PayPal publishes developer guidance on AP2; Worldline documents AP2 in its Connect AI docs. — [PayPal developer blog](https://developer.paypal.com/community/blog/PayPal-Agent-Payments-Protocol/); [Worldline docs](https://docs.connect.worldline-solutions.com/documentation/ConnectAI/agent-payments-protocol-ap2)

### Inferences
- AP2's open mandate is the closest existing primitive to a consumer "standing instruction" (e.g. "switch my electricity tariff whenever saving > EUR 100/yr, max 12-month term"): constraints signed once, agent executes later, with a non-repudiable evidence trail. It is defined for payments/checkout, not for contract conclusion or cancellation.
- The three-mandate vocabulary (intent/cart/payment) used in most 2025 press is outdated versus v0.2; the report should use both and explain the mapping (intent ≈ open mandate; cart ≈ closed checkout mandate).
- FIDO stewardship plus SD-JWT aligns AP2 technically with the EUDI wallet credential stack (SD-JWT VC), which makes an EU-wallet-held mandate plausible, but no source confirms an implemented bridge.

### Gaps
- Exact AP2 version/date in November 2026, the FIDO working group name and timeline could not be verified (fidoalliance.org and ap2-protocol.org blocked).
- No evidence found of AP2 mandates in production in Europe, nor of AP2 with SEPA direct debit or account-to-account payments.

## 3. Universal Commerce Protocol (UCP, Google with Shopify et al., Jan 2026)

### Takeaway
UCP is Google's Apache-2 commerce-workflow layer: merchants publish a capability profile at `/.well-known/ucp`, agents negotiate capabilities (checkout, cart, catalog, order, identity linking, plus extensions) over REST/MCP/A2A, and AP2 mandates plug in as an optional extension. It is live for US retail checkout in Google surfaces; the roadmap extends to food, lodging and grocery, but no regulated-services vertical was found.

### Cited Findings
- Announced January 2026 at NRF (coverage dated 13 Jan 2026) under Apache 2; co-developed with Shopify; endorsed by 20+ companies including Etsy, Wayfair, Target, Walmart and Visa. — [The New Stack](https://thenewstack.io/shopify-walmart-endorse-googles-new-open-commerce-protocol/); [FashionNetwork, 13 Jan 2026](https://uk.fashionnetwork.com/news/Google-rolls-out-its-universal-standard-for-ai-powered-commerce,1797225.html)
- Rollout: powers native checkout for eligible listings in AI Mode in Search and the Gemini app, initially US retailers; requires Google Merchant Center account and eligible feed; "Direct Offers" lets brands surface exclusive discounts. — [FashionNetwork](https://uk.fashionnetwork.com/news/Google-rolls-out-its-universal-standard-for-ai-powered-commerce,1797225.html)
- Discovery and capabilities: every business publishes a machine-readable profile at `/.well-known/ucp` declaring services, capabilities and payment handlers; named capabilities include `dev.ucp.shopping.checkout`, cart, catalog search/lookup, order, and `dev.ucp.common.identity_linking` (OAuth 2.0 account linking). — [UCP core concepts](https://ucp.dev/documentation/core-concepts/); [UCP overview](https://ucp.dev/specification/overview/)
- Spec versions seen: 2026-01-11, 2026-01-23, 2026-04-08, 2026-08-25. — [UCP 2026-04-08 overview](https://ucp.dev/2026-04-08/specification/overview/); [UCP AP2 mandates page](https://ucp.dev/latest/specification/ap2-mandates)
- AP2 extension: businesses opt in by declaring `dev.ucp.shopping.ap2_mandate` (a later page places it under `dev.ucp.common.payment.ap2_mandate`); mandates are SD-JWT credentials with key binding; UCP only defines where they sit in requests/responses. — [UCP AP2 mandates](https://ucp.dev/latest/specification/ap2-mandates)
- Shopify: transports REST, GraphQL, JSON-RPC, A2A, MCP; payment handlers such as Google Pay and Shop Pay; supports discounts, loyalty, subscriptions, fulfillment options, embedded checkout (marketing copy). — [Shopify UCP page](https://www.shopify.com/ucp)
- Roadmap (Google slides at a W3C e-commerce agents workshop, Sept 2026): extension beyond shopping into food ordering and lodging; adding grocery, fulfillment options, 3DS, location search; participants named include Stripe, Shopify, Google, Etsy, Wayfair, Microsoft, Target, Amazon, Meta, Salesforce. Planned, not confirmed shipped. — [W3C workshop slides, Amit Handa](https://www.w3.org/2026/09/ecommerce-agents/slides/Amit_Handa.pdf)

### Inferences
- UCP's capability-negotiation and namespaced extension model (`dev.ucp.<vertical>.<capability>`) is the most natural hook for defining new verticals (e.g. a hypothetical insurance-quote or energy-switch capability), since verticals such as food and lodging are already being added the same way. No one appears to have done this for regulated products.
- Identity linking via OAuth 2.0 gives a standard way for an agent to act inside a user's existing account at a portal, relevant to a comparison platform holding the customer profile.
- The presence of Stripe, Meta, Microsoft and Amazon on the UCP participant slide suggests convergence pressure between UCP and ACP, but no merger or formal interop was found.

### Gaps
- No evidence of UCP checkout live in Germany/EU.
- Spec not readable in this session; subscription semantics and the latest version's full capability list are unverified.
- Governance body for UCP (foundation vs. Google-led) not established.

## 4. MCP, A2A, NLWeb, llms.txt, WebMCP and other discovery mechanisms

### Takeaway
MCP is the de facto tool-connection layer and matured markedly in 2026: spec 2026-07-28 made the core stateless, hardened OAuth/OIDC authorization, and moved MCP Apps (UI) and Tasks into extensions, under Agentic AI Foundation (Linux Foundation) governance. A2A reached v1.0 in March 2026 with signed agent cards and joined AAIF in August 2026; WebMCP is in Chrome origin trial; llms.txt remains unadopted by major AI systems.

### Cited Findings
- MCP 2026-07-28 shipped as scheduled (release candidate locked 21 May 2026); Anthropic calls it the fifth spec release. Drops session state: removes the `initialize` handshake and `Mcp-Session-Id` header; any request can hit any server instance behind a round-robin load balancer. — [MCP blog, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [Claude blog](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)
- MCP Apps is an official extension evolving independently of the core release cycle; Tasks moved out of core into an extension. — [MCP blog, release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Authorization: six SEPs align with deployed OAuth 2.0 / OpenID Connect practice, e.g. clients must validate the `iss` parameter on authorization responses (SEP-2468, mix-up attack defence); Enterprise-Managed Authorization allows central management of authorization for MCP servers. — [AAIF: Authorization in MCP 2026-07-28](https://aaif.io/blog/authorization-in-mcp-2026-07-28-clarifying-trust-relationships-for-agentic-systems)
- Governance: MCP was contributed to the Agentic AI Foundation under the Linux Foundation in December 2025; the 2026-07-28 release adds a deprecation policy (reported 12-month clock for older versions). — [AAIF blog](https://aaif.io/blog/mcp-graduates-to-enterprise-infrastructure-stateless-architecture-formal-governance-and-security); [AAIF migration post](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate)
- Registry: an Okta announcement cites "nearly 2,000" MCP servers in the official registry (older figure, date unclear). — [Okta newsroom](https://www.okta.com/en-gb/newsroom/articles/cross-app-access-extends-mcp-to-bring-enterprise-grade-security-to-ai-agent-interactions/)
- A2A: donated by Google to the Linux Foundation June 2025; v1.0, first stable spec, shipped March 2026 with multi-protocol bindings, version negotiation, multi-tenancy and signed agent cards; 150+ supporting organizations and availability on Google, Microsoft and AWS platforms (9 Apr 2026); joined AAIF as a hosted project (17 Aug 2026). — [Linux Foundation press, 9 Apr 2026](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [AAIF: A2A joins AAIF](https://aaif.io/blog/a2a-joins-aaif)
- A2A discovery: agent card at `/.well-known/agent-card.json` (canonical); older material cites `/.well-known/agent.json`. — [specification.website: A2A agent cards](https://www.specification.website/spec/agent-readiness/a2a-agent-cards/)
- WebMCP: draft in the W3C Web Machine Learning Community Group (editors from Microsoft and Google); public origin trial Chrome 149-156; only consumer today is Gemini in Chrome; production support "probably 2027 at the earliest". PayPal (Sept 2026) offers WebMCP as an optional capability for Store Sync merchants (search, select, cart, initiate checkout). — [The New Stack](https://thenewstack.io/how-webmcp-lets-developers-control-ai-agents-with-javascript/); [heise](https://heise.de/-11178002); [PayPal developer blog](https://developer.paypal.com/community/blog/WebMCP_PayPal_Agent_Ready)
- llms.txt: proposed standard, not adopted by Google, OpenAI or other major LLM providers; Google's John Mueller called it "purely speculative"; generated by default by the AIOSEO WordPress plugin (3M+ sites). — [Search Engine Journal](https://searchenginejournal.com/mcp-a2a-nlweb-and-agents-md-the-standards-powering-the-agentic-web/570092/)
- NLWeb: open Microsoft project introduced at Build on 19 May 2025; schema.org-based natural-language endpoint with connectors to major LLMs; no confirmed 2026 status update found. — [VentureBeat](https://venturebeat.com/ai/the-battle-to-ai-enable-the-web-nlweb-and-what-enterprises-need-to-know/); [Search Engine Land](https://searchengineland.com/agentic-web-nlweb-schema-seo-asset-463778)
- Commerce-specific well-known files now exist in parallel: `/.well-known/ucp` (UCP) and `/.well-known/acp.json` (ACP 2026-04-17). — [UCP core concepts](https://ucp.dev/documentation/core-concepts/); [ACP changelog](https://agenticcommerce.dev/docs/changelog)

### Inferences
- For an agent-native comparison platform the practical surface stack in late 2026 is: a remote, stateless MCP server with OAuth (reachable from ChatGPT/Claude/Gemini-type hosts), an MCP App for rich comparison UI, an A2A agent card for agent-to-agent delegation, and UCP/ACP well-known profiles for transactional retail. llms.txt and NLWeb are low-cost but low-yield.
- The stateless MCP core fits high-volume price/tariff queries (horizontal scaling); long-running processes such as a supplier switch that completes days later map onto the Tasks extension or A2A tasks rather than core MCP.

### Gaps
- Current MCP registry size and governance details not verified; no reliable November 2026 figure.
- No source found on "agents.json" as a live standard.
- NLWeb's 2026 adoption is unknown.

## 5. Card networks, PSPs, stablecoin rails and European/German payment methods

### Takeaway
Agent payments in Europe in 2026 are card-network-led: Mastercard says all European issuers are network-enabled for Agent Pay and has run pilots in Germany (13 May 2026, Deutsche Bank, DZ Bank, N26); Visa runs its "Agentic Ready" programme in Europe since 17 March 2026 on the Trusted Agent Protocol. No source found shows a shipped agent-payment scheme on SEPA direct debit, Wero, invoice (Rechnung) or account-to-account rails, although these dominate German e-commerce.

### Cited Findings
- German online payment mix (EHI "Online Payment 2026", May 2026): PayPal 28.7% of online sales, purchase on account 26.1%, direct debit 14.4%, credit and debit cards 13.7%. — [DMEXCO](https://dmexco.com/stories/can-new-online-payment-provider-wero-challenge-paypal/)
- Mastercard Agent Pay: introduced April 2025 as a network-wide orchestration layer, "explicitly not a new wallet". - Worldline (Sept 2026) argues the industry must still establish how SCA applies when an authorised agent acts, proposing SCA at mandate set-up with autonomous execution within verified bounds. — [Worldline blog](https://worldline.com/en/home/main-navigation/resources/blogs/2026/agentic-payments-the-next-evolution-of-commerce-and-a-new-role-for-financial-institutions)

### Inferences
- Roughly 70% of German online payment volume (PayPal + Rechnung + Lastschrift) runs on methods with no documented agent-token scheme as of Nov 2026; the card-network programmes cover only the ~14% card share. This is a structural gap for any German agentic checkout.
- For the Check24 verticals (energy, insurance, telco, credit) the dominant payment instrument is a SEPA direct debit mandate given at contract conclusion, not a checkout payment. The relevant "agent payment" problem is therefore agent-collected SEPA mandate consent (and its evidential quality), not tokenised card checkout. No protocol found addresses this.
- Mastercard's network-level enablement means German cardholders are technically reachable without issuer projects, but everything reported for Germany is pilot/controlled.
- x402/stablecoin rails are oriented to machine-to-machine API and content micropayments in USD stablecoins; no source ties them to euro consumer purchases, so relevance to a German consumer switching platform is marginal (possible use: paying for data/API calls between agents).

### Gaps
- No sources found in this session on agentic programmes from Klarna, Adyen, Mollie or American Express (beyond Adyen and Amex being x402 Foundation members and Adyen an AP2 partner). Treat as unknown, not as absent.
- No source on PayPal Agent Ready availability in Germany, nor on PayPal's agent toolkit/MCP server status in 2026.
- No source on Wero or the EPC (SEPA schemes) publishing agent-payment rules; no source on agent-initiated SEPA e-mandates.
- No transaction volumes for any European agent-payment programme.

## 6. Agent identity and authentication

### Takeaway
Agent identity is splitting into a transport-level layer (Web Bot Auth: HTTP Message Signatures proving which agent operator sent a request; IETF working-group draft -01, 29 Oct 2026) and a delegation layer (KYA tokens, AP2/Verifiable Intent mandates, wallet-based credentials proving which human authorised what). The first is deploying via CDNs and Visa's Trusted Agent Protocol; the second is still drafts and pilots, and the EUDI wallet has no specified agent-delegation model yet.

### Cited Findings
- Web Bot Auth: IETF webbotauth working group draft `draft-ietf-webbotauth-httpsig-protocol-01` dated 29 Oct 2026 (authors T. Meunier, Cloudflare; S. Major, Google), previously `draft-meunier-webbotauth-httpsig-protocol`. Agent identifier is the HTTPS URL where it publishes keys, sent in a `Signature-Agent` header; `keyid` must be a JWK thumbprint; tag `web-bot-auth`; signatures cover authority or target URI plus created/expires. The protocol explicitly says nothing about who operates the agent, whether it is benign, or whether the request is authorised. — [IETF datatracker draft](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/); [draft -00 text](https://www.ietf.org/archive/id/draft-ietf-webbotauth-httpsig-protocol-00.html)
- Visa's Trusted Agent Protocol is being integrated by Cloudflare and Akamai. — [The Paypers](https://thepaypers.com/payments/news/visa-expands-agentic-commerce-access-for-merchants-across-europe)
- Skyfire KYA/KYAPay: IETF individual draft `draft-skyfire-oauth-kyapay-token-04` (updated 15 Nov 2026; authors Ankit Agarwal, Michael B. Jones) defines a signed JWT carrying agent, platform and human-principal identity claims; companion draft on using KYAPay tokens in OAuth flows; built on OAuth 2.0, JWT, JWKS; demonstrated with Visa Intelligent Commerce in 2025. — [IETF datatracker: KYAPay token](https://datatracker.ietf.org/doc/draft-skyfire-oauth-kyapay-token/); [KYAPay in OAuth draft](https://datatracker.ietf.org/doc/draft-skyfire-oauth-using-kyapay-tokens/); [Business Wire, 26 Jun 2025](https://www.businesswire.com/news/home/20250626772489/en)
- OpenID Foundation: AI Identity Management Community Group published "Identity Management for Agentic AI" (October 2025); the group does not itself develop protocol standards (deferred to OIDF/liaison working groups); its threat-modelling subgroup responded to NIST's RFI on AI agent security in March 2026. — [OpenID Foundation whitepaper](https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/); [OIDF AIIM community group](https://openid.net/cg/artificial-intelligence-identity-management-community-group/); [OIDF NIST response](https://openid.net/oidf-responds-to-nist-on-ai-agent-security/)
- MCP authorization is OAuth 2.0/OIDC-based with enterprise-managed authorization (see section 4). — [AAIF](https://aaif.io/blog/authorization-in-mcp-2026-07-28-clarifying-trust-relationships-for-agentic-systems)
- A2A v1.0 has signed agent cards for cryptographic identity verification. — [Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)
- EUDI wallet: every member state must provide at least one certified wallet by end of 2026; ENISA published a draft wallet certification scheme in April 2026; a CSA research note (AI-assisted, not officially reviewed) identifies the delegation model for AI agents as a gap. — [Cloud Security Alliance research note, Apr 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-enisa-eu-digital-wallet-ai-agent-identity/)
- WE BUILD large-scale pilot consortium argues the EU should coordinate integration of AI agents with EUDI and business wallets, with special attention to payments (Mar 2026); Aug 2026 coverage: EUDI wallet as "baseline target" for agentic-commerce standards. — [Biometric Update, Mar 2026](https://www.biometricupdate.com/202603/eu-can-rein-in-ai-agents-with-eudi-wallets-and-business-wallets-we-build); [Biometric Update, Aug 2026](https://www.biometricupdate.com/202608/eudi-wallet-provides-baseline-target-for-standards-to-enable-agentic-commerce)
- Dutch Payments Association held a workshop on agentic payments and the EUDI wallet. — [Betaalvereniging](https://www.betaalvereniging.nl/en/news/workshop-on-agentic-payments-and-the-eudi-wallet/)
- GLEIF working paper "Agentic AI in Payments" v1.0 (13 Aug 2026) proposes Agent Mandate Credentials (AMCs). — [GLEIF](https://www.gleif.org/organizational-identity/research-publications/2026-08-13_agentic_ai_in_payments_v1.0-1.pdf)

### Inferences
- Web Bot Auth answers "which platform's agent is this" but deliberately not "for whom and with what authority"; a comparison platform receiving agent traffic needs a second layer (OAuth identity linking, KYA token, or AP2 mandate) before releasing personalised quotes or accepting a contract.
- The EUDI wallet could in principle serve three roles for a German switching platform: verified identity attributes (PID) for quote data, qualified electronic signature for contract/mandate consent, and holder of an agent-delegation credential. Only the first two are in the wallet's specified scope; the third is proposal-stage.
- "KYA" is used by at least two parties with different meanings (Skyfire's token format; Mastercard's issuer-facing agent identification), so the report should not treat it as one standard.

### Gaps
- No OpenID Foundation or IETF standard for agent delegation is final; no source found on an adopted OAuth "on-behalf-of agent" extension.
- EUDI wallet rollout status in Germany as of Nov 2026 and any official position on agent delegation were not found.
- Cloudflare's own Web Bot Auth deployment figures not retrieved.

## 7. One-off retail checkout vs. recurring contracts, regulated products, rich-data quotes, cancellation/switching: explicit gap map

### Takeaway
Every shipped protocol is built around a one-off retail purchase of a priced SKU; recurring payments are claimed by AP2, ACP and UCP at the payment/subscription level, but no protocol found models contract conclusion for regulated products, quote requests needing rich personal data, pre-contractual information duties, cancellation of an incumbent contract, or a supplier switch. These are white space.

### Cited Findings
- ACP: launch scope single-item purchases; later carts and orders; vendor explainer says it covers physical and digital goods, subscriptions and asynchronous purchases. — [TechCrunch](https://techcrunch.com/2025/09/29/openai-takes-on-google-amazon-with-new-agentic-shopping-system); [Checkout.com](https://www.checkout.com/blog/agentic-commerce-questions-answered)
- AP2: spec claims standardized flows for recurring payments and subscriptions and human-not-present scenarios. — [AP2 specification](https://ap2-protocol.org/ap2/specification/)
- UCP: capabilities are checkout, cart, catalog, order, identity linking, discounts, fulfillment; roadmap verticals are food ordering, lodging, grocery. — [UCP overview](https://ucp.dev/specification/overview/); [W3C slides](https://www.w3.org/2026/09/ecommerce-agents/slides/Amit_Handa.pdf)
- PayPal Store Sync: physical goods to US customers in USD only. — [PayPal docs](https://developer.paypal.com/store-sync/overview)
- Merchants continue to rely on vault-based or network tokens for recurring payments, credential updates and lifecycle management; agent-scoped tokens "solve a different problem". — [BigCommerce](https://www.bigcommerce.com/articles/ecommerce/agentic-checkout/)
- Web Bot Auth does not convey authorisation. — [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/)
- A targeted search for agent protocols covering insurance or other regulated products returned nothing. — [PYMNTS vocab playbook (covers only commerce/payment layers)](https://www.pymnts.com/?p=4266062)

### Inferences
Gap map (inference from the cited scope statements; "not found" means no source in this session, not proof of absence):

| Need of an agent-native comparison/switching platform | ACP | UCP | AP2 | Card-network programmes | MCP / A2A |
|---|---|---|---|---|---|
| One-off retail checkout | Yes (core) | Yes (core) | Yes (authorization) | Yes | Transport only |
| Subscriptions / recurring payment | Claimed | Claimed (Shopify) | Claimed in spec | Existing network tokens | n/a |
| Standing instruction, human not present | Token limits only | Via AP2 extension | Yes (open mandates) | Agent-bound tokens | n/a |
| Quote from rich personal data (health, driving record, consumption, credit) | Not found | Not found | Not found | No | Generic tools only; schema must be custom |
| Regulated pre-contractual steps (advice, suitability, disclosures, withdrawal information) | Not found | Not found | Not found | No | Not found |
| Contract conclusion with later start date / underwriting / credit decision | Not found | Not found | Not found | No | Long-running tasks possible |
| SEPA direct debit mandate capture | Not found | Not found | Not found | No (cards) | Not found |
| Cancelling an incumbent third-party contract | Not found | Not found | Not found | No | Not found |
| Supplier/number switch orchestration | Not found | Not found | Not found | No | Not found |

- The asymmetry: payment authorization is over-served (ACP SPT, AP2, Visa, Mastercard, x402, KYAPay all address it), while "authority to conclude or terminate a contract on someone's behalf" (a power of attorney / Vollmacht in machine-verifiable form) is unserved. A switching platform's key missing primitive is a verifiable contracting-and-cancellation mandate, not a payment token.
- AP2's open-mandate construct and the GLEIF Agent Mandate Credential proposal are the nearest reusable designs for such a mandate.
- UCP's namespaced capability model is the most plausible place to standardise vertical capabilities such as quote, bind, cancel and switch.

### Gaps
- Could not verify in the primary specs what "subscriptions" concretely means in ACP and UCP (merchant-managed subscription product vs. agent-managed recurring mandate).
- No source found on any consortium working on agent protocols for insurance, energy or credit distribution.
- Regulatory treatment of agent-concluded regulated contracts (IDD advice duties, consumer credit rules, withdrawal rights) is outside this note's scope and was not researched.

## 8. Sector standards in insurance, energy and telco that agents could use (BiPRO, FRIDA, FiDA, MaKo/24h Lieferantenwechsel, number porting)

### Takeaway
The regulatory tailwind for open insurance data is fading: the Commission's 2027 work programme (adopted 4 Nov 2026) lists FiDA for withdrawal within six months, leaving industry initiatives (BiPRO, FRIDA e.V.) as the only standardisation path. German electricity has had the 24-hour technical supplier switch since 6 June 2025, but with API web services only for MaLo identification and §14a control commands, with the rest still EDIFACT, and with reported operational friction.

### Cited Findings
- FiDA: second trilogue June 2025, none since; Presidency questionnaire to member states with deadline 10 Apr 2026 on whether a realistic basis for progress exists; MLex (3 Nov 2026) reported the draft work programme would withdraw FiDA; Commission Work Programme 2027 adopted 4 Nov 2026 with 23 new initiatives and 18 pending proposals to be withdrawn within six months, FiDA among them, stated reason no trilogues since June 2025. Not yet formally withdrawn. — [Commission Work Programme 2027](https://commission.europa.eu/strategy-and-policy/strategy-documents/commission-work-programme/commission-work-programme-2027_en); [MLex](https://www.mlex.com/mlex/financial-services/articles/2545816/eu-commission-to-withdraw-financial-data-access-proposal-draft-shows-update-); [Regulation Tomorrow](https://www.regulationtomorrow.com/2026/11/european-commission-publishes-work-programme-2027/); [Council working paper](https://data.consilium.europa.eu/doc/document/WK-5041-2026-INIT/en/pdf)
- Earlier expectations that did not materialise: FiDA in force mid-2026 (CMS, Dec 2025). — [CMS](https://cms.law/en/deu/publication/2026-themen-die-sie-bewegen-werden/digitalisation-of-the-financial-sector-in-transition-key-developments-in-2026)
- FRIDA: registered as Frida (Free Insurance Data Initiative) e.V. in the Bundestag lobby register (first entry 20 Aug 2025, updated 15 Jul and 26 Oct 2026, no. R007550), purpose to accompany and shape FiDA implementation; works on an open interface standard for insurance data modelled on PSD2. No published API version found. — [Lobbyregister entry](https://www.lobbyregister.bundestag.de/media/cf/ab/865262/Lobbyregister-Registereintraege-Detailansicht-R007550-2026-10-26_10-05-44.pdf); [BSI Software](https://bsi-software.com/en/live/post/open-insurance-frida-spawns-innovation)
- BiPRO: association claims its data model and interface specifications largely cover FiDA requirements (self-assessment). Fincon Reply (Sept 2026) asks whether MCP-connected AI makes standards like BiPRO less necessary and says it is testing AI in the BiPRO context. — [BiPRO FiDA site](https://fida.bipro.net/en/?p=2150); [IT Finanzmagazin, 4 Sep 2026](https://www.it-finanzmagazin.de/?p=249559)
- 24h supplier switch: start moved by the Bundesnetzagentur from 4 Apr 2025 to 6 Jun 2025 (proceeding BK6-22-024); first API use cases are MaLo identification in the supplier switch and control actions under §14a EnWG. — [Bundesnetzagentur BK6-22-024](https://www.bundesnetzagentur.de/DE/Beschlusskammern/1_GZ/BK6-GZ/2022/BK6-22-024/BK6-22-024_EroeffnungVerfahren.html); [BDEW](https://www.bdew.de/energie/lieferantenwechsels-in-24-stunden/)

- Operational experience: Rabot Energy's CEO reports transmission errors, backlogs and high manual effort months after launch. — [Tagesspiegel Background](https://background.tagesspiegel.de/energie-und-klima/briefing/warum-der-24-stunden-lieferantenwechsel-nicht-reicht)
- 2026 API direction (single unverified commentary): Beschlusskammer 6 communicated in July 2026 a full replacement of UTILTS by API services, then on 1 Oct 2026 retained UTILTS; consulted web services for calculation formula and location bundle not introduced; API guideline stays as is; BDEW proposed 2029 for a MaBiS hub. — [innobu](https://www.innobu.com/de/buch-marktkommunikation-mako.html)
- Consumer-facing BNetzA information on switching exists. — [Bundesnetzagentur consumer portal](https://www.bundesnetzagentur.de/DE/Vportal/Energie/KuendigungLieferantenwechsel/Lieferantenwechsel/_FAQ_Lieferantenwechsel/table1.html)

### Inferences
- Energy is the vertical closest to "agent-executable switching": a regulated, deadline-bound, machine-to-machine switch process exists, and the new supplier (not the consumer) triggers it. But market communication is only open to registered market participants, so an agent platform acts through the supplier or a service provider; the consumer-side inputs an agent must supply are identification data (MaLo-ID / meter number, address) and a contract order with SEPA mandate.
- With FiDA likely withdrawn, there will be no legal right for a consumer (or their agent) to pull insurance contract data from incumbents via API; insurance comparison agents will depend on document upload/extraction, broker mandates (Maklervollmacht) and voluntary BiPRO/FRIDA interfaces. Banking data stays accessible under PSD2/PSD3 open banking.
- BiPRO is a B2B insurer-broker standard, so a platform with broker status can already use it for quote and application flows; wrapping BiPRO services as MCP tools is technically straightforward but is an inference, with no documented production example found.

### Gaps
- Telco number porting (TKG switching rules, porting processes and any API standard) was not researched in this session; no sources.
- No primary Bundesnetzagentur source retrieved for the 2026 UTILTS/API communications; gas-market switching timeline not checked.
- No hard 2026 statistics on switching duration or error rates.
- FRIDA technical deliverables (API specs, pilots) and BiPRO's current norm releases were not found.
- Formal FiDA withdrawal date unknown (planned within six months of 4 Nov 2026).
